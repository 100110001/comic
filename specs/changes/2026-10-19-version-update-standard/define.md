# 版本管理与应用更新标准草案

## 目标与状态

建立开发、评审、发版和客户端更新共用的判断标准，避免仅凭提交标题或发版人员记忆决定是否升级、是否强制更新。

本文是调研后的需求定义，供评审和后续实施使用，不代表强制更新已实现。现有行为仍以 `specs/settings.spec.md` 和 `specs/project-layout.convention.md` 为准；实施收割时形成正式的版本管理 convention，并更新有关规范和流程入口。

## 已有能力与问题

- `app/lib/screens/settings_screen.dart` 目前提供手动检查、下载和安装更新。
- `app/lib/models/update_info.dart` 只有最新版本、说明和平台下载地址，没有最低支持版本。
- `app/lib/services/update_service.dart` 按三个数字段比较版本，尚未提供强更判断。
- `scripts/release.ps1` 每次将应用构建号写成 `+1`，并未按注释所述递增。
- `.claude/commands/release.md` 默认建议补丁版本，尚未根据本次变更判断兼容性。
- 更新清单来自 `master`，发版 PR 合并后立即可见；安装包要等标签触发构建后才上传，存在先提示更新、后生成安装包的时间窗口。
- 漫画服务器地址可以自定义，而应用更新来源固定；应用最新版本不能单独代表每台服务器的兼容要求。

## 版本号标准

应用展示版本采用 `主版本.次版本.补丁版本`，构建号独立递增。

| 变更类型 | 版本处理 | 示例 | 更新判断 |
| --- | --- | --- | --- |
| 仅文档、CI 或开发工具变化 | 通常不发布应用 | 修改说明文档 | 不要求客户端更新 |
| 仅后端内部优化且保持协议兼容 | 通常不发布应用 | 优化查询和日志 | 不要求客户端更新 |
| 兼容的客户端修复 | 升补丁版本 | `1.2.1 → 1.2.2` | 默认可跳过 |
| 兼容的新功能 | 升次版本 | `1.2.1 → 1.3.0` | 默认可跳过 |
| 客户端与后端协议不兼容 | 升主版本 | `1.2.1 → 2.0.0` | 必须评估旧客户端停用范围 |

不兼容的判断对象是已发布客户端与目标后端之间的公开契约，包括接口、字段语义、图片交付和进度写入规则。后端内部函数重构不构成应用主版本升级理由。UI 改版或功能数量本身也不构成主版本升级理由。

同一发布中取最高变更级别；开发分支不为每次提交重复修改发布版本。构建号必须高于之前发布的构建号，不随主版本、次版本或补丁版本归零。首期正式发布只接受稳定的 `X.Y.Z`，不把预发布版本纳入自动更新通道。

## 强制更新策略

版本号表达兼容性，但 SemVer 本身不规定应用强制更新行为。先前讨论的“跨主版本强更”可作为基础方案，不能覆盖所有停用需求。

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 最新主版本高于当前主版本即强更 | 配置少，容易理解 | 同主版本严重缺陷难以停用；仍兼容的旧版本也会被一并拦截 |
| 当前版本低于最低支持版本即强更 | 可准确停用具体旧版本，允许同主版本紧急修复 | 发版时需要维护最低支持版本 |

建议采用最低支持版本方案，仍然完全通过版本号比较决定行为，不增加独立的强更布尔开关：

- R1. 当前版本低于最低支持版本时强制更新；当前版本不低于最低支持版本但低于最新版本时提供可跳过的更新提示。
- R2. 兼容发布默认继承上次最低支持版本；提高门槛必须记录原因和受影响版本，不能每次自动设置为最新版本。
- R3. 不兼容发布通常将最低支持版本提升至新的兼容主版本起点；同主版本出现严重缺陷时也允许提高门槛。
- R4. 最低支持版本不得高于可下载安装的最新版本；缺少本平台可安装包时不得发布新的强更门槛。
- R5. 普通更新检查超时或无效清单不阻断启动；已确认需要强更的会话不能通过下载失败、取消安装或返回操作解除拦截。
- R6. 强更页允许重试下载、重新检查和退出；安装器被唤起不等于安装成功，必须按实际运行版本判断是否解除拦截。
- R7. 更新要求按 Windows、Android 平台分别生效，Web 不使用原生安装包更新流程。

## 开发与评审标准

每项变更在需求、实施记录或 PR 中记录以下内容，避免维护第二份重复台账：

- 是否需要发布客户端；仅部署兼容后端或更新文档时允许填否。
- 建议版本级别：无、补丁、次版本、主版本，并说明依据。
- 旧客户端是否仍能正确运行，尤其关注字段删除、类型变化、分页与排序语义变化，以及写入行为。
- 是否需要提高最低支持版本；需要时记录原因、平台和最低可用版本。
- 是否要求后端部署、数据迁移或客户端发布的先后顺序。

自动检查负责字段完整性和版本一致性，不能从提交前缀或文件路径可靠推断业务兼容性。开发者提出判断，评审确认；发版时汇总上一正式版本后的全部变更。

## 发版标准

- R8. 发版流程先汇总变更记录，再建议版本号；存在不兼容变更时不得静默采用补丁版本。
- R9. 发布前检查应用、安装器、标签和更新清单版本一致，并核对构建号递增、最低支持版本合法、中文更新说明和强更原因完整。
- R10. 安装包构建成功并上传、核对版本与下载可用性后，才对客户端公布新版本和强更要求；构建失败不改变线上更新要求。
- R11. 需要停用旧协议时，先提供兼容的新客户端及可用更新路径，再停用旧协议；过渡期后端尽可能兼容新旧客户端。
- R12. 回退更新策略不能要求用户安装更低构建号的 Android APK；已安装的坏版本应通过更高版本修复。

已有发布命令和脚本应引用同一正式规范，避免各自维护版本判断规则。准备发版继续走独立分支和目标为 `master` 的 PR，由用户合并后发布。

## 旧客户端与自定义服务器

当前已发布客户端没有启动强更能力，修改远端清单不能让旧程序自动获得该能力。必须先发布带更新机制的过渡版本；未升级的更老客户端只能依靠后端兼容或明确拒绝不兼容请求，不能承诺统一显示强更页面。

应用分发更新策略与漫画服务器兼容要求需要区分。固定更新来源负责提供安装包；如果要保证任意自定义服务器的协议兼容，需由实际连接的服务器声明其兼容要求。仅凭全局最新版本无法证明服务器兼容，客户端也不能单独保证后端拒绝旧协议。

## 待确认事项

- 用户于 2026-10-19 确认最低支持版本方案，并授权继续计划与实现。
- 首期交付应用分发侧更新机制；实际漫画服务器的协议协商暂缓，不承诺检测任意自定义后端的兼容性。
- 保存最近一次有效清单，跨重启执行已知最低版本；首次检查失败放行，已有强更要求时断网不解除。新的有效清单允许撤回错误门槛。

## 验收场景

- 仅修改后端内部实现时，流程不会要求无意义的客户端发版。
- 兼容新功能与不兼容协议变化能在开发评审阶段得到不同版本建议。
- 同主版本普通修复可跳过；若选择最低支持版本方案，严重缺陷修复可准确拦截受影响旧版本。
- Windows 与 Android 更新包未就绪时，不发布对应强更要求。
- 检查断网、无效清单、下载失败和 Android 取消安装均有明确结果，不误报安装成功。
- 更新机制首次上线时明确过渡范围，不声称能够远程强制所有历史客户端升级。

## 规范影响与边界

后续实施需新增版本管理 convention，更新 `specs/settings.spec.md`、`specs/project-layout.convention.md`，并使开发入口、发布命令、脚本与 CI 引用同一标准。

本次交付为调研与标准草案，不修改运行代码、不实际发版、不提高线上更新门槛。文档引入新的设计决策，按非 trivial 变更处理；后续经计划、实现和收割后再将已落实规则写入正式规范。

## 调研依据

- [Semantic Versioning 2.0.0](https://semver.org/)：主版本表达公开 API 不兼容，次版本表达兼容功能，补丁版本表达兼容修复；不定义强制更新策略。
- [Android 应用版本管理](https://developer.android.com/studio/publish/versioning)：展示版本与构建版本分开，后续发布提高 `versionCode`；应用自身负责执行版本限制。
