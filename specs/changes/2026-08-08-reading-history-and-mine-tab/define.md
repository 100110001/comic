## Summary

拿掉应用内删除漫画的能力（前端和后端都去掉），把"我的" tab 从接口调试面板改造成"最近阅读"+"收藏"两个列表，并新增阅读进度（精确到页）与收藏的持久化数据。为了让这些数据能在重新扫描导入后依然有效，后端导入流程从"每次清空重建"改为增量导入。

## Problem Frame

当前"我的" tab（`lib/screens/mine_screen.dart`）是一个纯接口调试面板——几个按钮用来手动测 `/api/health` 之类接口、看 JSON 响应，对日常使用没有价值。

应用没有任何形式的阅读记录：看到哪本漫画的第几话第几页，全靠自己记，数据库 schema（`backend/src/db/schema.sql`）里也只有 `comics`/`chapters`/`images` 三张表，没有用户数据的位置。收藏同理，完全没有。

漫画详情页（`lib/screens/detail_screen.dart`）有一个删除按钮，对应后端 `DELETE /api/comics/:id`（`backend/src/routes/comics.ts`）——删除时连本地文件夹一起清掉，不可恢复，且这个接口没有任何鉴权。后端 `app.use(cors())`（`backend/src/app.ts:10`）对所有来源开放，而这个应用平时也会用浏览器访问 Web 版，所以恶意网页的脚本理论上可以直接触发这个删除请求。

此外，`backend/src/db/init.ts` 目前在每次运行导入流程（`npm run setup`）时都会先 `TRUNCATE` 掉 `comics`/`chapters`/`images` 三张表再重新导入——这意味着即使加上阅读进度/收藏数据，只要重新导入一次，所有漫画的数据库 ID 就会重新分配，导致这些记录全部失效或错误关联。

## Key Decisions

- **直接移除删除功能，而不是加固它。** 曾考虑给删除接口加来源限制和确认头来防止恶意网页触发，但这只解决"被动触发"，不解决"自己手滑删错且不可恢复"。移除后，删漫画的方式变成手动删除磁盘上的文件夹再重新扫描——更麻烦，但两类风险都不存在了。
- **不做软删除/回收站。** 既然应用内删除本身被拿掉，就不需要保留误删找回的机制。
- **导入流程从"清空重建"改为增量导入。** 这是阅读进度/收藏能持久化的前提：只要还在清空重建，ID 就会漂移，进度/收藏必然失效。增量导入需要能在多次扫描之间稳定识别"这是同一本漫画/同一章节/同一图片"，具体匹配方式留给规划阶段设计。
- **阅读进度粒度是"每本漫画一条最新记录"，不是每章节各留一个断点。** 用户翻看旧章节时，"最近阅读"会覆盖更新到这个新位置，不同时保留多个断点。
- **导入时发现磁盘上消失的漫画，只提示、不自动清理。** 避免外置存储没挂载时被误判为"漫画都被删了"而清空对应数据；代价是消失但未清理的记录会残留，需要用户自己不定期处理。

## Requirements

**移除删除功能**

- R1. 漫画详情页不再提供删除入口（现有的删除按钮和确认对话框整体移除）。
- R2. 后端不再提供删除漫画的接口。

**"我的" tab 重做**

- R3. 现有的接口调试面板（`mine_screen.dart` 当前的全部内容）整体移除。
- R4. "我的" tab 展示两个列表：最近阅读、收藏。
- R5. 点击"最近阅读"中的某一项，直接进入阅读器并定位到该漫画记录的具体章节和页码。
- R6. 点击"收藏"中的某一项，进入该漫画的详情页。

**阅读进度与收藏**

- R7. 应用记录用户在每本漫画上最近一次阅读到的章节和页码，每本漫画只保留一条最新记录。
- R8. 用户可以在漫画详情页对某本漫画进行收藏或取消收藏，收藏是漫画级别的，不区分章节。

**导入流程增量化**

- R9. 重新运行导入流程时，已存在的漫画/章节/图片对应的数据库 ID 保持不变，不因为重新导入而改变。
- R10. 导入流程只新增磁盘上新出现的漫画/章节/图片，不重复插入已经存在的内容。
- R11. 导入流程发现数据库中的某本漫画在磁盘上已经找不到对应文件夹时，在扫描输出中提示，不自动从数据库删除该漫画及其章节/图片记录。

## Key Flows

- F1. 继续阅读
  - **Trigger:** 用户在"我的" tab 点击"最近阅读"列表中的一项。
  - **Steps:** 应用读取该漫画记录的最新阅读位置（章节 + 页码）→ 打开该章节的阅读器 → 定位到记录的页码。
  - **Covered by:** R5, R7

- F2. 收藏切换
  - **Trigger:** 用户在漫画详情页切换收藏状态。
  - **Steps:** 更新该漫画的收藏标记 → "我的" tab 的收藏列表随之更新。
  - **Covered by:** R6, R8

## Acceptance Examples

- AE1. **Covers R5, R7.** Given 用户正在阅读《XXX》第 3 话第 10 页，When 用户退出后从"我的"点击"最近阅读"里的《XXX》，Then 应用直接打开第 3 话并定位到第 10 页。
- AE2. **Covers R7.** Given 用户此前记录的最新阅读位置是第 5 话，When 用户主动翻回第 2 话阅读，Then 阅读记录更新为第 2 话的位置，不再同时保留第 5 话的记录。
- AE3. **Covers R11.** Given 数据库中存在漫画 A，但其对应文件夹已从磁盘删除，When 重新运行导入流程，Then 漫画 A 仍保留在数据库和应用列表中，扫描输出中标注该漫画未在磁盘找到。

## Scope Boundaries

Deferred for later:

- 阅读器交互增强（页码提示、上一话/下一话跳转、缩放或阅读方向设置）。
- 首页漫画列表的排序/筛选功能。
- 测试覆盖和 CI 补全。

Outside this round:

- 除删除接口外，其余只读接口的 CORS 开放策略不做收紧——这轮通过移除删除功能本身规避了对应风险。

## Dependencies / Assumptions

- 增量导入依赖一种能跨多次扫描稳定匹配"同一漫画/章节/图片"的方式；现有的 `INSERT IGNORE`（`backend/src/scripts/seed.ts`）实际上依赖每次清空重建来避免重复，本身并没有能防止重复插入的唯一约束，具体的匹配和去重机制留给规划阶段设计。
- 收藏与阅读进度是单机、单用户级别的全局数据——应用没有账号/登录体系，不需要按用户区分。
