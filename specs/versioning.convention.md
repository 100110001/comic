# 版本管理与应用更新

## 职责

统一开发评审、版本命名、客户端更新和发布顺序。应用版本的事实源为 `app/pubspec.yaml`；后端内部包版本不作为应用强更依据。

## 版本分级

| 变更 | 版本处理 | 默认更新要求 |
| --- | --- | --- |
| 纯文档、CI、开发工具 | 通常不发布应用 | 无 |
| 兼容协议的后端内部优化 | 通常只部署后端 | 无 |
| 兼容的客户端修复 | patch：`1.2.1 → 1.2.2` | 可跳过 |
| 兼容的新功能 | minor：`1.2.1 → 1.3.0` | 可跳过 |
| 客户端与后端公开协议不兼容 | major：`1.2.1 → 2.0.0` | 明确评估最低支持版本 |

- 同次发布取最高变更级别；次版本升级重置补丁为零，主版本升级重置次版本和补丁为零。
- 兼容性以已发布客户端能否继续正确读写为准，包括字段类型、字段语义、图片交付和进度写入；UI 改版、功能数量或内部函数重构不单独决定主版本。
- 正式自动更新通道只接受稳定的 `X.Y.Z`，数字段不带前导零；不发布预发布版本。
- `+构建号` 独立递增，不随版本级别归零；Android 构建号为正整数且不超过 2100000000。同一展示版本不通过增加构建号重复发布给自动更新通道。

## 开发与评审

涉及行为的变更在需求、实施记录或 PR 中记录以下信息；PR 模板提供统一入口，不另建重复台账：

- 是否需要客户端发版，以及原因。
- 建议版本级别：无、patch、minor、major，并说明依据。
- 旧客户端是否兼容，受影响的行为和版本。
- 最低支持版本保持或调整；调整时说明平台、版本和原因。
- 后端部署、数据迁移与客户端发布顺序，或注明无要求。

自动校验检查版本和元数据一致性，业务兼容性由开发与评审判断。不能从提交前缀或改动目录自动推断兼容性。发布命令汇总上一正式版本以后的全部变更，再提出版本建议；不默认选择补丁。

## 更新契约

- 更新以当前应用版本和当前平台的 `minimumSupportedVersion` 比较：低于最低版本必须更新；不低于最低版本但低于 `latestVersion` 时可稍后更新；等于或高于最新版本不提示更新。
- 不使用独立的强更布尔值，不以跨主版本作为唯一拦截规则。同主版本的严重缺陷也可提高最低版本；跨主版本是否停用旧版本仍需明确判断。
- Windows、Android 各自具有最低版本与下载地址；最低版本不得高于最新版本。旧清单缺少最低版本时不强更；不支持的平台与 Web 不采用原生更新包。
- 清单保持 `latestVersion`、`releaseNotes` 和 `platforms.<平台>.downloadUrl`；平台可包含 `minimumSupportedVersion`、`minimumSupportReason`。发布清单另记录 `buildNumber`、`changeType`、`compatibilityNotes` 供校验与审计。
- 客户端拒绝非稳定版本、最低版本越界和非 HTTPS 或带 user-info 的下载地址；无本平台下载包的清单不替换该平台已确认的更新要求。
- 更新源固定为 `https://github.com/100110001/comic/releases/latest/download/update.json`，与漫画服务器地址独立。

## 启动、缓存与安装

- Windows/Android 的 release 构建在业务页面及进度补传初始化前检查更新；debug/profile 不自动检查，设置页仍可手动检查。检查请求有 15 秒超时。
- 启动与设置页共用更新状态。强更门覆盖全部路由，业务导航树卸载，返回、鼠标侧键、下载失败、安装取消均不能解除要求；仅提供下载、重新检查和退出。
- 普通更新可稍后处理，提示不丢弃已有业务路由状态。Windows 使用现有静默安装流程，Android 唤起系统安装器；唤起成功不等同于安装成功，当前运行版本仍低于门槛时保持拦截。
- 最近有效清单保存在版本化本地偏好 `appUpdateManifest.v1`，启动先恢复缓存再联网。首次检查失败且没有有效缓存时允许使用；已有强更要求时，失败和断网保持限制。
- 新有效清单可降低或撤回错误门槛；清单保存失败不解除本次有效限制，但提示下次启动需要联网，不保证跨重启保留此次更新要求。
- 更新安装操作和检查互斥，失败后可重试；不同时发起多个安装下载。

## 发布流程

- `scripts/release.ps1` 要求 `Version`、`ChangeType`、`CompatibilityNotes`、`Notes`，在独立分支、干净的已跟踪工作区与暂存区运行。
- 两平台最低版本默认继承上一清单；历史清单缺失时以 `0.0.0` 表达不限制，避免首次引入字段就停用历史版本。按需传入 `WindowsMinimumVersion` 或 `AndroidMinimumVersion`；提高门槛必须提供 `MinimumSupportReason`。
- 发布脚本校验版本递增、级别一致、最低版本合法后，同步应用版本、安装器、更新清单与更新日志；构建号加一，检查 Git 退出码，生成提交和本地标签。
- 准备 PR 以 `master` 为目标，由用户合并；合并后只推送已核对的版本标签，不在准备阶段自动发布。
- `scripts/validate-release.ps1` 核对版本源、构建号、清单、安装器、更新日志和下载地址；CI 同时相对上一祖先发布标签校验递增及门槛调整原因。
- 标签 CI 构建 Windows 与 Android，创建或复用同版本 draft Release，上传 `comic-setup.exe`、`app-release.apk`、`update.json`；重新下载并核对文件非空、清单及安装包哈希后，才发布并设为 latest。
- 正式 Release 不原地覆盖；草稿失败可重试，任一构建或上传校验失败不公布新的更新要求。禁止把低于已发布稳定版本的 Release 重新设为 latest。
- 本地自动上传通道不保留；发布统一经标签 CI。`scripts/test-release.ps1` 在临时仓库验证准备与资产校验，不发布真实安装包。
- 停用旧协议前应先提供兼容的新客户端及下载路径，再部署停用；回退应用缺陷采用更高版本和构建号，不要求 Android 安装更低构建号的 APK。

## 边界与已知差距

- 从未安装本更新机制的历史客户端不具备启动强更能力，远端清单不能为旧程序补上能力。上线先提供过渡版本，后端仍需处理更老客户端。
- 历史客户端读取 `master/releases/update.json`，仅有手动更新；该地址在发版 PR 合并后可能早于安装包就绪。新客户端只读取已发布 Release 资产，规避此时间窗口。
- 固定分发更新源不能证明自定义漫画服务器的兼容性；当前没有服务器协议协商或服务端旧版本拒绝机制。本规范不承诺检测任意自定义后端的兼容要求。
- 当前校验保证发布文件与上传资产一致，不读取 APK 内部版本元数据，也不替代设备上的覆盖安装验证。

## 依据

- [SemVer 2.0.0](https://semver.org/) 规定公开 API 的兼容性分级，不定义应用强制更新行为。
- [Android 版本管理](https://developer.android.com/studio/publish/versioning) 区分展示版本与构建号，应用自身执行版本限制。
